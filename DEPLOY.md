# DEPLOY.md — production deployment

**Stack:** Render (API, Docker) · Neon (PostgreSQL 16) · Vercel (frontend) · Cloudflare R2 (files) · Firebase Auth (Google).

ARCHITECTURE.md §6 explains why: WeasyPrint needs system libraries, so the API needs a Docker host. Neon's free Postgres doesn't expire. R2 has no egress fees for PDF downloads.

Allow about 45 minutes. Do the steps in order, because later steps need values from earlier ones.
Placeholders look like `<THIS>`.

---

## 0. Prerequisites

- The repo pushed to GitHub (Render and Vercel deploy from it).
- Accounts on Google/Firebase, Neon, Cloudflare, Render and Vercel. All have free tiers; Cloudflare R2 asks for a card even on its free tier.

---

## 1. Firebase (Google sign-in)

1. Go to https://console.firebase.google.com, click **Add project**, and name it `maritimer`. Analytics is optional.
2. Open **Build → Authentication → Get started → Sign-in method → Google**, click **Enable**, choose a support email, then **Save**.
3. Open **Project settings (gear) → General → Your apps → Web (`</>`)**, register app `maritimer-web` without hosting, and copy:
   - `apiKey` → `VITE_FIREBASE_API_KEY`
   - `authDomain` → `VITE_FIREBASE_AUTH_DOMAIN` (e.g. `maritimer-xxxx.firebaseapp.com`)
   - `projectId` → `VITE_FIREBASE_PROJECT_ID` and the backend `FIREBASE_PROJECT_ID`
   - `appId` → `VITE_FIREBASE_APP_ID`
4. Open **Authentication → Settings → Authorized domains** and click **Add domain**. Add your Vercel domain after step 5, e.g. `maritimer.vercel.app`. `localhost` is already listed.
5. The backend only needs the project ID to verify ID tokens; Google's public keys are fetched automatically. A service account is **not** required.
   - Optional, only if you want revocation checks (`FIREBASE_CHECK_REVOKED=true`): open **Project settings → Service accounts → Generate new private key**.
   - Then run `base64 -i key.json | tr -d '\n'` and put the output in `FIREBASE_SERVICE_ACCOUNT_JSON_BASE64`.

## 2. Neon (PostgreSQL)

1. Go to https://console.neon.tech and click **New project**. Use Postgres **16** and a region close to Render's (e.g. *AWS ap-southeast-1 Singapore*).
2. On the project dashboard click **Connect**. Leave **Connection pooling off** to get the *direct* connection string. It looks like:
   `postgresql://<user>:<password>@<endpoint>.<region>.aws.neon.tech/neondb?sslmode=require`
   This is `DATABASE_URL`. Use the direct string, not the `-pooler` one.
   - The database driver (psycopg 3) automatically reuses prepared statements, which a transaction-mode pooler can break.
   - Migrations also belong on a direct connection.
   - The app opens only a few connections (2 workers, reused for 60 s), well within Neon's direct-connection limit.
3. The migrations create the `citext` extension themselves; Neon allows it. Note the role name (`<user>`) for `AUDIT_LOG_REVOKE_ROLE`.

## 3. Cloudflare R2 (file storage)

1. In the Cloudflare dashboard, open **R2 → Create bucket**, name it `maritimer-files` with location *Automatic*, and keep it **private**: no public access.
2. Open **R2 → Manage R2 API Tokens → Create API token** with permission *Object Read & Write*, scoped to `maritimer-files`. Copy:
   - Access Key ID → `S3_ACCESS_KEY_ID`
   - Secret Access Key → `S3_SECRET_ACCESS_KEY`
   - The S3 endpoint `https://<ACCOUNT_ID>.r2.cloudflarestorage.com` → `S3_ENDPOINT_URL`
3. No bucket CORS is needed. Downloads are short-lived presigned URLs (5 minutes) opened in a new tab, and uploads go through the API.

## 4. Render (API)

1. Go to https://dashboard.render.com and choose **New → Blueprint**. Connect the GitHub repo; Render reads `render.yaml`.
2. When prompted, fill in the `sync: false` variables:

| Variable | Value |
|---|---|
| `DJANGO_ALLOWED_HOSTS` | `maritimer-api.onrender.com` (the Render hostname is also added automatically) |
| `DATABASE_URL` | Neon **direct** connection string from step 2 (pooling off) |
| `FIREBASE_PROJECT_ID` | from step 1 |
| `CORS_ALLOWED_ORIGINS` | `https://<your-app>.vercel.app` (set after step 5; comma-separate several) |
| `CORS_ALLOWED_ORIGIN_REGEXES` | `^https://<your-app>-[a-z0-9-]+\.vercel\.app$` (Vercel preview deploys, optional) |
| `S3_BUCKET_NAME` | `maritimer-files` |
| `S3_ENDPOINT_URL` | from step 3 |
| `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` | from step 3 |
| `BOOTSTRAP_ADMIN_EMAIL` | **your own Google email**: becomes the first Admin, and is idempotent |
| `AUDIT_LOG_REVOKE_ROLE` | Neon role name. Optional hardening that makes `audit_log`, `dispute_events` and `fx_rates` append-only at DB level |

   `DJANGO_SECRET_KEY` is generated by Render, and `DJANGO_SETTINGS_MODULE=config.settings.prod` is preset.
3. Click **Apply**. The first build takes about 5 minutes because it installs WeasyPrint's system libraries.
   On every start, `bin/start.sh` runs `migrate`, then `seed_masterdata`, then `bootstrap_admin` if `BOOTSTRAP_ADMIN_EMAIL` is set, then gunicorn.
4. Verify:
   ```bash
   curl https://maritimer-api.onrender.com/api/v1/health      # {"status":"ok"}
   ```
5. Free-tier note: the service sleeps after 15 minutes idle, and the first request after that takes about 30 seconds. To avoid it, ping `/api/v1/health` every 10 minutes from a free monitor such as cron-job.org or UptimeRobot, or use Render's Starter plan.
6. Optional scheduled job: request expiry needs `python manage.py expire_requests` hourly.
   - On Render: **New → Cron Job**, same repo, root `backend`, Docker, command `python manage.py expire_requests`, same env vars. Render cron jobs are paid, from about $1/month.
   - Requests without `expires_at`, the default from the UI, never expire, so this job is optional.

## 5. Vercel (frontend)

1. Go to https://vercel.com/new, import the repo, and set **Root Directory** to `frontend`. The framework is detected as Vite; `vercel.json` sets the build and SPA rewrites.
2. Add **Environment Variables** (Production and Preview):

| Variable | Value |
|---|---|
| `VITE_API_BASE_URL` | `https://maritimer-api.onrender.com/api/v1` |
| `VITE_FIREBASE_API_KEY` | from step 1 |
| `VITE_FIREBASE_AUTH_DOMAIN` | from step 1 |
| `VITE_FIREBASE_PROJECT_ID` | from step 1 |
| `VITE_FIREBASE_APP_ID` | from step 1 |
| `VITE_DEV_AUTH` | **leave unset** (or `false`) in production |

3. Click **Deploy**, then note the domain, e.g. `https://maritimer.vercel.app`.
4. Go back and finish the cross-references:
   - **Firebase → Authentication → Settings → Authorized domains**: add `maritimer.vercel.app`.
   - **Render → maritimer-api → Environment**: set `CORS_ALLOWED_ORIGINS=https://maritimer.vercel.app`. Render redeploys.

## 6. First sign-in and demo data

1. Open the Vercel URL, click **Continue with Google**, and use the `BOOTSTRAP_ADMIN_EMAIL` account. You land on the Admin dashboard.
2. Optional demo data, so every role can be shown. Each demo role needs its **own Google account**.
   Google signs in the base account, so Gmail `+` aliases do **not** work here.
   Use separate Gmail accounts, Google Workspace users, or any existing email registered as a Google Account (accounts.google.com → *Create account* → *Use my current email address instead*).
   In the Render dashboard, open **maritimer-api → Shell** and run:
   ```bash
   python manage.py seed_demo \
     --admin-email you@gmail.com \
     --owner-email <owner-google-email> \
     --agent-email <agent-google-email> \
     --merchant-emails <pilots-email>,<supplies-email>,<customs-email>
   ```
   Render's free plan has no shell. Instead, run the same command locally with the production `DATABASE_URL` and the S3 variables, because demo invoices upload PDFs:
   ```bash
   cd backend && DJANGO_SETTINGS_MODULE=config.settings.prod DJANGO_SECRET_KEY=x FIREBASE_PROJECT_ID=<id> \
     DATABASE_URL='<neon-uri>' STORAGE_BACKEND=s3 S3_BUCKET_NAME=maritimer-files S3_ENDPOINT_URL=<r2-endpoint> \
     S3_ACCESS_KEY_ID=<key> S3_SECRET_ACCESS_KEY=<secret> .venv/bin/python manage.py seed_demo --owner-email … 
   ```
   Each address becomes a pre-approved user, linked on that account's first Google sign-in. Roles you don't have accounts for can still be shown locally with dev sign-in.
3. Real users can now sign in with Google, choose a role, complete onboarding and upload documents. You approve them under **Admin → Approvals**.

## 8. CORS and security checklist

- `CORS_ALLOWED_ORIGINS` lists only your Vercel domain(s). Credentials are off; auth is a Bearer header.
- Firebase **Authorized domains** include the Vercel domain. Otherwise the Google popup fails with `auth/unauthorized-domain`.
- `VITE_DEV_AUTH` is unset on Vercel, and production Django ignores dev tokens regardless.
- The R2 bucket is private. Files are served only through 5-minute presigned URLs after a permission check.
- Optionally set `AUDIT_LOG_REVOKE_ROLE` and redeploy, so the migration revokes UPDATE/DELETE on audit tables.

## 9. Updating

Push to the default branch. Render rebuilds the API and runs migrations on start; Vercel rebuilds the frontend. Pull requests get Vercel preview URLs, which the CORS regex allows.

## 10. Troubleshooting

| Symptom | Fix |
|---|---|
| `auth/unauthorized-domain` on sign-in | Add the domain in Firebase → Authentication → Settings → Authorized domains |
| Browser console: CORS error | `CORS_ALLOWED_ORIGINS` on Render must exactly match the site origin (scheme + host, no trailing slash) |
| `401 Invalid or expired token` | `FIREBASE_PROJECT_ID` on Render must match the frontend's `VITE_FIREBASE_PROJECT_ID` |
| `403 not_approved` after sign-in | Expected for new users. Approve them in Admin → Approvals, or make sure `BOOTSTRAP_ADMIN_EMAIL` is your email |
| PDF download 500 | Check Render logs. The image must include pango (it does); R2 credentials must allow writes |
| First request slow | Render free tier cold start (§4.5) |
